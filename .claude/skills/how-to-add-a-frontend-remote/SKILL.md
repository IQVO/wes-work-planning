# How to add a frontend remote

Use when adding a new screen/feature to this repo's `web/` Module
Federation remote (`planning-mfe`), or when standing up a NEW remote for a
bounded context that doesn't have one yet. This is the Vite/React
micro-frontend layer that `warehouse-console` (the shell) lazy-loads at
`/planning/*` as `planning_mfe` — see that repo's shell-side MFE contract
for the other half of this.

## `web/vite.config.ts` must stay in OBJECT form, always

This repo's actual `web/vite.config.ts`:

```ts
const IS_BUILD = process.argv.includes("build");
const PUBLIC_BASE = IS_BUILD ? "/mfes/wes-work-planning/" : "/";

export default defineConfig({
  base: PUBLIC_BASE,
  plugins: [react(), federation({ name: "planning_mfe", filename: "remoteEntry.js", exposes: { "./App": "./src/App.tsx" }, /* ... */ })],
  server: { port: 5183, strictPort: true, cors: true, origin: "http://localhost:5183" },
  // ...
});
```

Never convert this to the callback form
(`defineConfig(({ command }) => ({...}))`) to compute `base` dynamically —
read the command off `process.argv` instead, exactly as above. The
fleet-wide reason this matters: a remote whose `vitest.config.ts` does
`mergeConfig(viteConfig, ...)` throws `Error: Cannot merge config in form
of callback` on a function `vite.config.ts` export, killing the whole test
suite for a one-line config change. This repo's own `web/vitest.config.ts`
happens to be standalone today (see below) rather than merging
`vite.config.ts`, so the trap wouldn't currently bite here — but the object
form is still the fleet-wide convention every other remote depends on, and
`vite.config.ts`'s own comment records this as the deliberate reason it's
written this way. Keep it that way in case a future test needs the React
or federation plugin config and switches to `mergeConfig`.

## `web/vitest.config.ts` is deliberately standalone here, not merged

Unlike some sibling remotes, this repo's `vitest.config.ts` does NOT
`mergeConfig` against `vite.config.ts`:

```ts
export default defineConfig({
  test: { include: ["src/**/*.test.ts"] },
});
```

The file's own comment explains why: the only tests here are pure unit
tests of the runtime endpoint resolver (`src/config.ts`), which need
neither the React plugin nor the Module Federation plugin — importing
`vite.config.ts` would pull both in for no benefit. No `jsdom` environment
either; `src/config.ts` guards its `window` access so the resolver runs
fine under vitest's default node environment. Follow this pattern for a
new pure-logic test file; reach for `mergeConfig` (and jsdom) only when a
test actually needs to render a component or touch the DOM.

## A tiny, relative `dist/remoteEntry.js` after build is CORRECT

After a build with the `/mfes/wes-work-planning/` base, `dist/remoteEntry.js`
is a small relative re-export — grepping it for `/mfes/wes-work-planning/`
returns zero matches. That is expected, not a bug: `dist/index.html`
carries the absolute prefixed URLs, every JS chunk uses relative ESM
imports, and the module-preload helper resolves relative to wherever
`remoteEntry.js` was actually fetched from — exactly what a path-mounted
remote needs. Verify correctness by serving the built image and fetching
through the real gateway path (`http://localhost/mfes/wes-work-planning/`),
never by grepping the built file for the expected prefix.

## `@warehouse/ui-kit` is a sibling checkout, not a registry package

`web/package.json` depends on it via `"@warehouse/ui-kit":
"file:../../warehouse-ui-kit"`. Any domain-status color, chart, or shared
layout primitive belongs in that repo, not hand-rolled here — a remote
reinventing its own palette instead of consuming the shared kit is a bug,
not a style choice.

## This remote DOES have a `test` script — confirm any new remote does too

`web/package.json`'s `"test": "vitest run"` is already wired here (unlike
several other remotes in this fleet that historically shipped only
build/dev/lint/preview and silently never ran added `.test.ts` files).
Confirm `npm run` still lists `test` before assuming a new test file
executes, and confirm the CI `web:` job (`.github/workflows/ci.yml`)
actually calls `npm test`, not just `npm run build` — it does today
(`web:` job: `npm run lint`, `npx tsc -b`, `npm test`, `npm run build`, in
that order, against a dual checkout of this repo plus
`claudioed/warehouse-ui-kit@develop`).

## The Docker build recipe (packaging as a deployable nginx workload)

`web/Dockerfile` is the complete, working, heavily commented recipe in
this repo — copy it rather than re-deriving these traps from scratch:

1. **Base image is `node:22-bookworm-slim`, not alpine or a newer node.**
   This repo's `package-lock.json` was generated by npm 10 on macOS and
   carries no linux entries for Vite 8's platform-specific optional
   dependencies (`@rolldown/binding-linux-*`, `lightningcss-linux-*`,
   `@oxlint/binding-linux-*`). npm 11 (node:26) rejects that lockfile
   outright with `EUSAGE "lock file out of sync"`; Debian/glibc matches
   the published `*-gnu` bindings.
2. **The lockfile is deliberately NOT used to install, in either build
   stage.** npm/cli#4828: a lockfile missing an optional dependency for
   the current platform won't install it even under plain `npm install`,
   so the build still dies with "Cannot find native binding". Both the
   `uikit-build` stage and the remote's own `build` stage do
   `rm -rf node_modules package-lock.json && npm install --no-save`
   (direct dependency versions still come from `package.json`'s ranges;
   the committed lockfile is never read for resolution or mutated).
3. **`@warehouse/ui-kit` must be supplied as a named BuildKit context**,
   since it's a sibling checkout, not a registry dependency:
   ```bash
   docker build --build-context uikit=../../warehouse-ui-kit \
     -t warehouse/wes-work-planning-frontend:local .
   ```
4. Runtime stage is `nginxinc/nginx-unprivileged:1.31-alpine` with a root
   `apk upgrade --no-cache` step (picks up CVE fixes published since the
   base image was last rebuilt) before dropping back to the `nginx` user —
   matches `warehouse-console`'s own runtime stage convention.

## Wiring into `warehouse-infra`'s deploy

A new remote isn't deployed automatically — `warehouse-infra`'s
`local.services` map and this repo's own Helm chart
(`charts/wes-work-planning`, `frontend.enabled` value) both need updating.
See `warehouse-infra`'s AGENTS.md for the Terraform side of this; this repo
only needs to ship a working chart with `frontend.enabled` wired to a
toggle.

## Key commands

```bash
cd web
npm ci
npm run lint        # oxlint
npx tsc -b           # typecheck
npm test             # vitest run — confirms this actually runs your new test
npm run build         # tsc -b && vite build -> dist/
```

CI's `web:` job runs this exact sequence against a dual checkout (this
repo + `claudioed/warehouse-ui-kit@develop`) — reproduce that locally by
checking out `warehouse-ui-kit` as a real sibling if `npm ci` behaves
differently than CI. Note the `web:` job in this repo's `ci.yml` currently
runs unconditionally on every push/PR (unlike `helm-lint`/`trivy-scan`,
which are gated to `pull_request` targeting `main` only) — check the
current workflow file before assuming that scoping if this guide goes
stale.
